# 1. Project Overview（プロジェクト概要）

DealerOS は全国 GYEON ディーラー向けのマルチテナント SaaS。本依頼は、その**見積作成/編集画面**を **7スクリーンのウィザード UI** として再デザインするもの。

- 現行の「1画面スクロール型エディタ」を、**画面ごとに1つの関心事**へ分割する。
- **対象範囲は見積ウィザードの Screen1〜Screen7 のみ。** 予約カレンダー・代車・請求書・納品書・保証書は本 UI パッケージの対象外（別スペックで設計）。
- **本再設計の目的は「機能追加」ではない。** 使いやすさの向上とオペレーターのストレス軽減。
- **committing 操作（確定操作）の数を絶対に増やさない。**

---

# 2. Design Philosophy（デザイン哲学）

- **プロフェッショナルな業務ツール**。ダーク基調のみ。装飾より情報密度・操作速度・視認性。
- **1スクリーン＝1関心事**。縦スクロールを最小化する。
- **視覚的明瞭さ ＞ コンパクトさ**（衝突時は常に明瞭さを優先）。
- **押しボタン式の選択**：オペレーターは**プルダウンを開かずに、いま何が選択されているかを常に把握できる**。
- **タッチ最優先**：現場でタブレット/スマホ操作を想定。48×48px 以上のタップ領域。
- **現場ワークフロー最優先**：エンジニア都合・見た目都合よりも現場効率。

---

# 3. Target Users（対象ユーザー）

- **主ユーザー：APU（ディテーラー／オペレーター）**。施工現場・受付カウンターで、手袋・明るい屋外・片手操作などの条件下で使う。
- **デバイス**：デスクトップ（受付PC）、タブレット（現場）、スマートフォン（移動・出張見積）。
- **リテラシー**：反復操作に習熟したプロ。muscle memory（操作の手癖）を尊重し、学習コストを増やさない。
- **顧客**：APU の客。画面には直接触れないが、備考・見積提示・LINE 送付の対象。

---

# 4. UI Principles（UI 原則・binding）

1. **プルダウン禁止**：Screen3 以降はプルダウン（ドロップダウン/`select`）を**全面禁止**。選択は**視覚ボタン**で行う。Screen1〜2 の選択（顧客検索結果・ボディサイズ等）も**ボタン式**（後述）。ウィザード内にネイティブ・プルダウンを置かない。
2. **選択状態が常時可視**：選択中は塗り＋境界で明示、非選択は淡い境界。「開かないと分からない」UI を作らない。
3. **committing 操作を増やさない**：遷移ボタン・確認ダイアログの追加で確定操作数を増やさない。
4. **muscle memory 保持**：ラベル・順序・コントロール位置を一貫させる。新規/編集で見た目を変えない。
5. **必須項目ハイライト**：必須（`*`）が未入力の間は **Amber** で強調し、入力完了で通常（白系）に戻す。
6. **自由ナビゲーション**：任意スクリーンへ1タップでジャンプ可（トップナビ）。
7. **自動保存**：キャンセル以外のアクションは自動保存。

**スクリーン順序は確定・不変**：`1 顧客登録 → 2 車両登録 → 3 作業内容選択 → 4 見積 → 5 値引き/クーポン → 6 備考 → 7 確認`。統合・分割・並べ替え・削除は不可。

## Screen 1 — Customer Registration（顧客登録）

**目的**：顧客の特定・登録。**必須は「登録方式」と「顧客名」のみ。他は任意。**

### 入力順
1. **登録方式** `*`（**押しボタン3種**、択一）
   - `手入力（新規顧客登録）` — **新規見積開始時のデフォルト選択**。
   - `車検証OCR`（AI-OCR で読み取り。読み取り後は全項目を自動入力し、オペレーターが自由修正可）
   - `既存顧客を検索`（**押下時のみ**検索モーダルを開く。§Screen1-検索）
   - `**` **デフォルトは「手入力（新規顧客登録）」**。オペレーターは**いつでも**「車検証OCR」「既存顧客を検索」へ切替可能。
2. **お客様名 / 会社名** `*` — テキスト（ph「山田太郎 / 株式会社〇〇」）
   - `**` 入力から**フリガナを自動生成**して隣接の「フリガナ」欄に反映（修正可）。
3. **郵便番号** — テキスト（ph「000-0000」）
   - `**` 郵便番号→住所 自動入力、住所→郵便番号 逆引きの双方向。
4. **住所** — テキスト（ph「都道府県・市区町村・番地」）
5. **電話番号** — tel（ph「090-0000-0000」）
6. **LINE ID** — テキスト（**手入力 or QR読み取り**）
   - `**` **QR読み取りボタンは、APU が店舗設定で LINE Business アカウントを登録している場合のみ表示**。

`**` **Screen1 の SNS 系は「LINE ID」と「LINE QR取得」のみ。** WhatsApp・Instagram・X 等の他 SNS の ID 入力欄は**今回は配置しない**（現場で使わない項目を増やして入力画面を煩雑にしないため）。ただし**将来 SNS を追加できる拡張設計**とする。通信（送信）は見積完成後に行うため、**通信ボタンは Screen1 に置かず Screen7 に集約**する。

### 業者 / 掛売り（独立した2ボタン）
- **`業者`ボタン** → ON で **値引率（%）** 入力を表示。
- **`掛売り`ボタン** → ON で **締め日 → 支払条件** を順に入力表示。
- `**` 2つは**独立**（どちらか一方でも両方でも可）。

### `**` 補足（デザイン制約・機能は不変）
- **信販会社の専用 UI（ボタン/トグル）は作らない。** 法人は通常の顧客として登録する。信販会社と判定された場合は、実際の車両使用者を内部的に顧客とする（バックエンド処理・UI不要）。
- OCR で取得した内容はフォームへ自動入力し、**全項目を自由に修正可能**。

### Screen1-検索（検索モーダル / オーバーレイ）
- **検索ボタン押下時のみ**開く。
- 検索キー：**名前 / フリガナ / 電話 / 住所（大まかで可）/ ナンバープレート下4桁**。
- **検索結果は選択可能なボタンで表示**（プルダウン不可）。タップで顧客を選択。

## Screen 2 — Vehicle Registration（車両登録）

**目的**：車両の登録と**ボディサイズ確定**。

### 入力方式
- **`車検証OCR`** or **`手入力`**（押しボタン択一）。

### 入力順
1. **ナンバープレート** `*` — テキスト（ph「滋賀 330 に 1234」）
2. **メーカー** `*` — テキスト（ph「トヨタ / ポルシェ / ニッサン」）`**` 車検証では「社名」と表記。
3. **車名** `*` — テキスト（ph「クラウン / 5シリーズ / GT-R」）`**` **車検証から取得不可のため、常に手入力必須**。
4. **型式**
5. **車体番号**
6. **初年度登録年月**
7. **登録年月日**
8. **ボディカラー**
9. **車検満了年月日**

### ボディサイズ（3M推定 → 7ボタン）
- **7段階を押しボタンで配置**：`SS / S / M / ML / L / LL / XL`。
- ワークフロー：
  1. OCR → 2. 車両寸法（長さ・幅・高さ）取得 → 3. **3M計算** → 4. **推奨サイズのボタンをハイライト** → 5. **APU が最終決定**。
- `**` **ハイライトはあくまで推奨。ボディサイズは絶対に自動確定しない。最終決定権は常にオペレーター。**

## Screen 4 — Estimate Editor（見積）

**目的**：Screen3 で選択したカテゴリのみを表示し、見積を作成する。

### 共通ルール
- **プルダウンを一切使わない。全選択は押しボタン。**
- **レイヤー構造を先頭で決めてから選択する**（単層選択時は2層・3層のボタンを**グレーアウト**）。
- **PPF を選択していた場合は、Screen4 内で「フル施工 / 部分施工」を押しボタンで分岐**して表示する（Screen3 では分けない）。
- **PPF＋コーティング**選択時はコーティング費用が減額される場合がある（店舗設定の**減額補正**値を適用し、結果金額を表示）。

### 店舗オプション（グローバル・完全に動的）
- **追加サービスオプション**として配置（コーティング限定ではなく全般に適用）。
- **初期状態のデフォルト表示（例題）**：鉄粉除去 / ハードポリッシュ / 傷補修 / ヘッドライトリペア / タッチペン。
- `**` **オペレーターカスタマイズは DealerOS の中核概念。** デフォルトは**例題として初期登録されているだけ**であり、各ディテーラー店舗は店舗設定から自由に **名称変更・追加・削除・価格変更**できる。
- `**` **UI は「オプション一覧が動的（可変）である」前提でデザインする**（項目数・名称・価格は店舗ごとに異なる）。ハードコード前提のレイアウトにしない。

### コーティング — レイヤー選択マトリクス（確定・UIのみ）
1層目のコーティング剤に応じて2・3層目の選択肢が変わる。**ショップランクは店舗設定由来。**

**GYEONショップ**
- 単層：`Q² ONE EVO` / `Q² CANCOAT EVO`
- 2層：`Q² ONE EVO` の場合 → `Q² ONE EVO` or `Q² CANCOAT EVO`（2種のみ）

**GYEONディテーラー**
- 単層：`Q² ONE EVO` / `Q² PURE EVO` / `Q² MOHS EVO` / `Q² SYNCRO EVO` / `Q² MATTE EVO`
- 2層：
  - `Q² ONE EVO` → `Q² ONE EVO` or `Q² CANCOAT EVO`（2種）
  - `Q² PURE EVO` → `Q² PURE EVO` or `Q² CANCOAT EVO`（2種）
  - `Q² MOHS EVO` → `Q² MOHS EVO` or `Q² CANCOAT EVO`（2種）
  - `Q² MATTE EVO` → `Q² MATTE EVO`（1種）
  - `Q² SYNCRO EVO` → デフォルト2層構造のため `Q² MOHS EVO` のみ追加可
- 3層：
  - `Q² ONE EVO` → `Q² CANCOAT EVO`（1種）
  - `Q² PURE EVO` → `Q² CANCOAT EVO`（1種）
  - `Q² MOHS EVO` → `Q² CANCOAT EVO`（1種）

**GYEONサーティファイドディテーラー**
- 単層：`Q² ONE EVO` / `Q² PURE EVO` / `Q² MOHS EVO` / `Q² SYNCRO EVO` / `Q² MATTE EVO` / `Q² INFINITE BASE TYPE 1` / `Q² INFINITE BASE TYPE 2`
- 2層：
  - `Q² ONE EVO` → `Q² ONE EVO` or `Q² CANCOAT EVO`（2種）
  - `Q² PURE EVO` → `Q² PURE EVO` or `Q² CANCOAT EVO`（2種）
  - `Q² MOHS EVO` → `Q² MOHS EVO` or `Q² CANCOAT EVO`（2種）
  - `Q² MATTE EVO` → `Q² MATTE EVO`（1種）
  - `Q² SYNCRO EVO` → デフォルト2層構造のため `Q² MOHS EVO` のみ追加可
  - `Q² INFINITE BASE TYPE 1` → `Q² INFINITE BASE TYPE 1` or `Q² INFINITE TOPCOAT TYPE 1` or `TYPE 2`
  - `Q² INFINITE BASE TYPE 2` → `Q² INFINITE BASE TYPE 2` or `Q² INFINITE TOPCOAT TYPE 1` or `TYPE 2`

  - `Q² ONE EVO` → `Q² CANCOAT EVO`（1種）

  - `Q² MOHS EVO` → `Q² CANCOAT EVO`（1種）

### PPF — 種類リスト（確定）と流れ
- **グロス・プロテクション（光沢・透明）**：`PPF PROTECT+` / `PPF ENHANCE` / `PPF HYBRID`
- **マット・ステルス（艶消し）**：`PPF MATTE`

- 流れ：**PPF選択 → 施工する PPF種類を選択 → 店舗設定の施工係数を掛ける → 価格計算 → 結果表示**。
- `**` GYEON 以外の PPF を施工する APU も想定（種類は店舗設定で拡張可能に）。
- `**` 将来の PPF 原価計算（3M計算＋在庫DB仕入価格）は**本フェーズ対象外**（拡張余地のみ）。

### その他カテゴリ（現行ロジック維持・ボタン化のみ）
- **ウィンドウフィルム / ボディ定期メンテナンス / 洗車 / ルームクリーニング / その他作業**：業務ロジックは現行どおり。**プルダウンをボタン式に置換するのみ。**

### 明細
- 各カテゴリの選択・追加で明細行を生成し、**数量・割引・行の追加/削除**を編集可能（現行どおり）。金額は右揃え・桁区切り。

- `**` **各ナビゲーションボタン（予約カレンダー・請求書・納品書・納品請求書）は自動保存の後、対応するモジュールへ遷移する正式な入口**（プレースホルダ/スタブではない）。遷移先の画面自体は本パッケージ対象外（別スペック）。

### 通信ボタン領域（Screen7 に集約・拡張可能）
- **通信は見積完成後に行うため、通信ボタンは Screen7 のみに配置**する（Screen1 には置かない）。
- **`LINE` は常時表示**。表記は状態で出し分け：
  - LINE Business API **設定済** → **「LINE送信」**
  - LINE Business API **未設定** → **「LINE文章コピー」**
  - どちらも送付用文章（挨拶文＋見積内容）を自動生成。
  - `**` **LINE挨拶文（デフォルトテンプレート）は店舗設定から編集可能**。**見積内容の本文は常に自動生成**（編集対象は挨拶文テンプレートのみ）。
- **`WhatsApp` / `Instagram` / `X`** は**今回未実装**。各 API が店舗設定で登録された時点で **Screen7 に自動追加**されるよう、**拡張可能な配置設計**にしておく（今回はアクティブ UI として描かない）。
- `**` **保証書（コーティング/PPF）は施工完了後にのみ表示**（見積ウィザード段階では非表示・本パッケージ対象外）。
- `**` 既存見積の修正時は、登録済みの施工内容・価格・数量・オプションを初期状態で表示。

# 7. Tablet UI（768–1023px）

- Sticky Total は**下部固定バー**（「合計のみ + タップで内訳シート」）。
- タップ 48×48px、入力 `text-base`。

# 8. Smartphone UI（<768px）

- ステッパーは**コンパクト**（例「3 / 7 作業内容」+ ドット進捗）。**タップで展開＝ボトムシート**で全スクリーン一覧（片手操作・iOS標準的）。

- **スワイプ移動**：左スワイプ＝次スクリーン、右スワイプ＝前スクリーン。**Back/Next ボタンも併設**（スワイプは追加手段でボタンを置き換えない）。ドット進捗はスワイプでも同期。横スクロール要素（明細テーブル等）とスワイプが競合しないよう配慮。
- Sticky Total は**下部固定バー**（合計のみ + タップで内訳シート）。
- OCR / LINE QR は**フルスクリーンに近い集中オーバーレイ**。
- 48×48px タップ、`text-base` 入力（iOS ズーム防止）。

# 11. Bottom Navigation（ボトムナビ）

- **全ページに `戻る` / `次へ` を設置**（Back＝左、Next＝右、位置は全ステップ固定）。
- `次へ` は前進ゲートのみで**必須ブロックしない**（未入力でも進める）。**確定検証は保存時に一括**。
- Tablet/Smartphone は**下部固定アクションバー**（保存等の主要 CTA を含む）。
- **Tablet/Smartphone はスワイプ移動（左＝次／右＝前）に対応**（§7/§8）。**スワイプは Back/Next の代替ではなく追加手段**で、両者は常に併存する。スワイプ移動は committing 操作にカウントしない。

# 12. Sticky Total Panel（常設合計パネル）

- **全スクリーンで常時可視**（Screen7 だけに隠さない）。
- 内訳：カテゴリ別小計（表示のみ）/ 小計 / 値引き / 消費税（税率%）/ **合計**（最も強いコントラスト）。
- **展開度**：Desktop は常時展開／モバイル（Tablet・Smartphone）は「合計のみ + タップで内訳シート」。
- 価格計算中の**ローディング状態**を用意。金額は桁揃え（tabular-nums）。

# 13. Icons and Illustrations（アイコン・イラスト）

- **ステップアイコン7種**：顧客（人）/ 車両（車）/ 作業（スパークル or ツール）/ 見積（明細リスト）/ 値引き（タグ or %）/ 備考（メモ）/ 確認（チェック）。
- **アクション**：保存 / PDF / LINE / 予約カレンダー / 請求書 / 納品書 / 追加（＋）/ 削除（ゴミ箱）/ 編集。
- **OCRフロー**：車検証アップロード（カメラ/書類）/ スキャン中 / レビュー（確認）。
- **通信**：LINE / WhatsApp / Instagram / X（ダークUIに調和）。**LINE QR**：QR提示オーバーレイの枠。
- **状態**：完了（チェック）/ 現在地 / エラー（amber/red）/ ローディング（スピナー）。
- スタイル：**線画中心・ダーク背景で視認性の高いストローク**。過度な装飾・フルカラーイラストは避ける。
- **空状態**：テキスト＋小さな線画アイコンのみ（装飾ゼロ）。

# 14. Button Design（ボタン設計）

- **選択は押しボタン式**（chip / セグメント / 選択カード）。**選択中は塗り＋境界で明示**、非選択は淡い境界。多数レコード（顧客検索結果等）は**タップ選択リスト**。
- **状態5種**：default / hover / active / disabled / loading（保存中・アップロード中の文脈表示可）。
- **プライマリ**（保存等）＝ `#1d4ed8` 系。**セカンダリ** ＝ `slate-700` 系。**追加アクション**（明細に追加等）＝ blue アウトライン。
- **破壊的操作（行削除等）に確認ダイアログを追加しない**（committing 操作を増やさないため）。誤タップ対策は**間隔・配置・「元に戻す」トースト**で。
- タップ領域 48×48px 以上。角丸 `rounded-lg`。

---

# 15. Spacing（余白・密度）

- カード内 `p-5` 基準。角丸 `rounded-lg`（入力/ボタン）/ `rounded-xl`（カード）。
- セクション間は視認可能な余白を確保しつつ、冗長な空白は避けスクロールを削減。
- ただし**視覚的明瞭さ ＞ コンパクトさ**：詰めすぎて選択状態が読みにくくなるより、余白を取り明瞭にする。
- タップ領域最小 48×48px。

---

# 16. Typography（タイポグラフィ）

- 既定 sans-serif（日本語可読性優先）。
- 見出し：小型・大文字トラッキング（`text-xs font-semibold uppercase tracking-wider text-slate-400` 相当）。
- ラベル：`text-xs font-medium text-slate-400`。
- 入力/本文：**`text-base`（モバイル・iOS ズーム防止）** / `sm:text-sm`（デスクトップ）。
- 金額：桁揃え（tabular-nums）。合計は最大ウェイト/コントラスト。密なテーブルは `text-xs`〜`text-sm`。

# 18. Animation（アニメーション）

- **控えめ・高速**（業務効率優先）。過度なモーション不可。
- スクリーン切替：軽いフェード/スライド（150–200ms）。
- 合計金額の更新：短い色/背景パルス（点滅不可）。
- auto-advance（後述）時：**1〜1.5秒の軽いトースト**で移動先を通知（追加操作は付けない）。
- ローディング：スピナー or スケルトン（OCR処理中・計算中・保存中）。
- オーバーレイ（OCR/QR）：フェードイン＋軽いスケール、閉じるは即時。
- `prefers-reduced-motion` を尊重。

# 19. Responsive Rules（レスポンシブ規則）

- ブレークポイント：**Mobile `<768` / Tablet `768–1023` / Desktop `1024+`**。
- Desktop＝2カラム（入力＋右 Sticky Total）。Tablet＝単カラム＋下部合計バー。Mobile＝単カラム＋コンパクトステッパー＋下部合計バー。
- 広い要素（明細テーブル等）は各自 `overflow-x: auto` 内でスクロール（**本文の横スクロール禁止**）。
- **スワイプ移動（Tablet/Smartphone のみ）**：左＝次スクリーン／右＝前スクリーン。**Back/Next ボタンと併存**。横スクロール領域上ではその領域のスクロールを優先し、スクリーン遷移スワイプと競合させない（Desktop はスワイプ非対応・ステッパー＋Back/Next）。

# 20. Dark Mode（ダークモード）

- **ダークモードのみ。ライトモードは作成しない。** 全画面・全ブレークポイントをダーク基調で統一（§17 トークン）。

# 21. Accessibility（アクセシビリティ）

- タップ領域 48×48px 以上、入力 `text-base`（iOS ズーム防止）。
- コントラスト確保（ダーク背景でテキスト/選択状態が明瞭）。
- 選択ボタン/トグルに `aria-pressed` 等の状態を持たせ、選択状態を支援技術にも伝える。
- キーボード操作・フォーカス可視。
- `prefers-reduced-motion` 対応。
- 必須項目の Amber ハイライトは、色だけに依存せず `*` マーク併記で伝える。

---

# 22. Operator Workflow（オペレーター・ワークフロー）

- **新規/編集の統一 UX**。編集時は登録済みデータを初期表示。
- **自由ジャンプ**：トップナビで任意スクリーンへ移動可。
- **auto-advance**：既存の committing 操作に前進を同居させ、遷移専用クリックを新設しない（例：既存顧客をタップ選択→車両へ、OCRレビュー確定→車両へ、明細追加→見積へ）。移動は軽いトーストで可視化。
- **自動保存**：キャンセル以外のアクションで自動保存。
- **修正**：該当スクリーンへ戻り、入力済みデータを保持したまま編集。
- **committing 操作の定義**（数える）：顧客/車両/サービス選択・データ入力・明細追加・値引き/クーポン適用・保存・PDF/LINE/予約・請求書系。（数えない）：スクロール・ステップ遷移・ページ間移動・パネル/ステップの開閉。
- **未保存ガード**：ページ離脱（ブラウザバック/リロード/タブ閉じ）時のみ確認。ウィザード内ステップ移動では警告しない。

# 23. Things GenSpark MUST NOT change（GenSpark が変更してはならないこと）

## 絶対禁止
GenSpark は以下を**してはならない**：
- ワークフローの再設計
- ステップの統合 / 分割
- スクリーン順序の変更
- ボタンの削除
- 機能の削除
- ボタンをプルダウンに置換すること
- 業務ロジックの簡略化
- 業務ルールの再設計

## 変更してよいのは以下のみ
- 見た目（visual appearance）/ レイアウト / 配色 / アイコン / イラスト / 余白 / タイポグラフィ / アニメーション

## UI ルール（再掲）
- **Screen3 以降はプルダウン禁止。選択は視覚ボタンで行う。オペレーターは常にいま何が選択されているか把握できること。**
- **優先順位**：直感的操作・視覚的明瞭さ・オペレーターのストレス最小化。**視覚的明瞭さ ＞ コンパクトさ。**
- **committing 操作を絶対に増やさない。**
