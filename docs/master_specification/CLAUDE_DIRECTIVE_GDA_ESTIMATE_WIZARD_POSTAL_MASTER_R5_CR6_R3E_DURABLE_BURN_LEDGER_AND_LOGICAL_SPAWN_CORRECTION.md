## 9. Logical process adapter versus real OS spawn

Frozen `apply-once.mjs` must remain unchanged. Its call to
`adapters.process.spawn()` is a **logical adapter call**, not proof that an OS
process was created.

After frozen preflight returns an accepted plan, the outer adapter performs
the same internal target validation once before lock/burn. On mismatch it
acquires no lock and writes no burn record, but invokes frozen `applyOnce()`
with a mismatch-only process adapter so the frozen core records its normal
target-mismatch quarantine. On an exact target it acquires the project lock,
completes the durable burn transaction, and only then invokes `applyOnce()`.
The logical process adapter repeats target validation immediately before each
possible real launch to close time-of-check/time-of-use drift.

For each logical call, the production adapter first validates the executable,
complete argv/token positions, fixed project ref, real workdir/cwd identities,
environment, stage order, burn state, lock ownership, and remaining deadline.

If any identity differs, the injected logical `process.spawn()` must:

1. invoke no `node:child_process.spawn`, executable, shell, network, or CLI;
2. return a synthetic handle implementing the frozen `onExit`, `terminate`,
   and `waitForExit` interface;
3. deliver exactly one asynchronous `onExit` result with
   `targetMismatch:true`, `code:null`, `signal:null`,
   `promptDetected:false`, and `ledgerMismatch:false`; and
4. make `terminate` and `waitForExit` deterministic no-process operations.

Thus the frozen core observes its one logical `spawn()`/`onExit()` cycle and
returns target-mismatch quarantine, while the count of real OS/Supabase
process launches is exactly zero. Tests must assert both counters separately.

For an exact target, the list logical call may invoke one real OS process only
after Section 8's lock and durable burn transaction. The up logical call may
invoke at most one real process only after exact list success and while the
same lock remains owned. No other stage, fallback, direct SQL, retry, repair,
