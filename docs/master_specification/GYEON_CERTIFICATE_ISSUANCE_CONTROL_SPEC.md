## 1. 目的

GYEON製品を使用していない施工への保証書発行、購入量に対して不自然に多い発行、他店舗名義の発行などを防止する。

保証書・施工証明書の発行をDealerOSへ集約し、Office AZ / GYEON Japanが次をいつでも確認できる状態にする。

- 誰が、いつ、どの店舗で発行したか
- どの顧客・車両・施工・製品に対して発行したか
- どの製品購入から発行可能枠が付与されたか
- 発行前後の残り発行可能枚数
- 再発行、訂正、失効、管理者調整の履歴
- 発行時点のPDF、規約、ロゴ、PDFハッシュ
- 公開照合ページでの有効・失効状態

## 2. 帳票区分（準確定）

| 帳票 | 対象 | 発行枠 | 備考 |
|------|------|--------|------|
| **ボディコーティング保証書** | 保証対象として管理者が登録したボディ用ベースコーティング | ベース製品の発行枠を1台につき1枠消費 | トップコートは併記できるが、原則として追加枠を消費しない |
| **CanCoat専用保証書** | CanCoatの管理者指定SKU | CanCoat専用の発行枠を1台につき1枠消費 | 汎用施工証明書ではなく、専用保証書を使う |
| **コーティング施工証明書** | レザー、ガラス、ホイール等の保証書対象外コーティング | 原則として保証書発行枠を消費しない | 発行履歴と施工製品は記録する |
| **PPF施工証明書／製品保証書** | PPF施工 | PPF用の独立ルール | ボディコーティング発行枠とは分離する |

### 2.1 ボディコーティング保証書の記載ルール

- 保証書には、実際に施工したボディ用コーティングだけを記載する。
- ベースコーティングとトップコートを区別して記載する。
- 発行枠を消費する基準製品は、原則としてベースコーティングとする。
- レザー、ガラス、ホイール等を同じ保証書へ混在させない。
- 施工明細に存在しない製品は選択も発行もできない。

### 2.2 CanCoat

- CanCoatは専用保証書を使用する。
- 添付デザイン内の「保証書ではない」という文言は、現在の事業決定と矛盾するため採用しない。
- CanCoat EVO / PRO等の対象SKU、保証期間、保証条件は管理者の商品ルールで個別管理する。

## 3. 商品別発行ルール

スーパーアドミンは、製品またはSKUごとに次のルールを設定する。

| 項目 | 内容 |
|------|------|
| 商品・SKU | GYEONの商品マスターに紐づく一意な製品 |
| 帳票種別 | ボディ保証書 / CanCoat保証書 / 施工証明書 / PPF帳票 |
| 保証対象 | 保証書を発行できるか |
| 発行可能枚数 | 購入単位1件あたりに付与する整数枠 |
| 製品役割 | base / top / standalone / certificate_only |
| 許可ランク | Certified / Detailer / Shopのどの店舗が発行できるか |
| 保証期間・条件 | 適用する保証規約バージョン |
| 有効状態 | 新規発行に使用できるか |
| 適用開始・終了 | ルール変更の有効期間 |

- 発行可能枚数は商品ごとに異なる。
- 過去の発行済み帳票へ新しいルールを遡及適用しない。
- ルール変更後も、発行済み帳票は発行時点のスナップショットを保持する。
- 小数の発行枠は使用せず、購入確定時に付与する整数枚数を管理する。

## 4. 発行可能枠の管理

### 4.1 残高式

```text
発行可能残高
  = 購入確定による付与
  + スーパーアドミン調整による加算
  - 保証書発行による消費
  - 返却しない失効分
  - スーパーアドミン調整による減算
```

### 4.2 台帳方式

現在値だけを上書きするカウンターは禁止する。すべての増減を追記型台帳として保存する。

台帳には最低限、次を記録する。

- dealer_id
- product_rule_id / product_id / sku
- entry_type（purchase_grant / issuance_debit / admin_adjustment / approved_refund）
- 増減枚数
- 取引後残高
- 元になった購入、発行、取消申請のID
- 実行者、実行日時、理由
- 冪等性キー

### 4.3 購入との接続

- 初期実装では、スーパーアドミンが確認済み購入を登録し、商品ルールに従って枠を付与できる。
- 将来のB2B受発注・在庫管理完成後は、確定購入データから自動付与する。
- 注文作成だけでは付与せず、出荷・売上確定など管理者が定める確定状態で付与する。
- 同じ購入を複数回処理しても二重付与されないこと。
- この発行枠は在庫数量とは別の管理対象であり、在庫の簡易版として実装しない。

### 4.4 店舗表示

店舗は商品ごとに次を確認できる。

- 現在の発行可能残高
- 付与済み枚数
- 使用済み枚数
- 直近の増減履歴
- 残高不足、失効、発行停止の理由

他店舗の残高・履歴は参照できない。

## 5. 発行条件

保証書は、次の条件をすべて満たす場合だけ発行できる。

1. 認証済みユーザーが有効な店舗メンバーである。
2. 店舗が有効で、保証書発行を停止されていない。
3. 店舗ランクが商品ルールの許可範囲に含まれる。
4. 元となる作業が完了済みである。
5. 顧客、車両、施工日、施工製品が確定している。
6. 対象製品が作業明細に存在する。
7. 対象製品が有効な商品ルールに登録されている。
8. 必要な発行可能残高がある。
9. 同一作業・同一車両・同一基準製品に有効な保証書が重複していない。
10. 適用する保証規約バージョンが有効である。

クライアントから渡されたdealer_id、店舗ランク、製品権限、残高、ロゴURLを信用しない。すべてサーバー側で再解決する。

## 6. 発行トランザクション

発行は、単一のDBトランザクションまたは同等の原子的RPCで実行する。

```text
1. 認証主体と店舗を確定
2. 対象作業・車両・製品・ランクを検証
3. 商品別発行残高をロック
4. 重複発行を再検証
5. 一意な連番を採番
6. 発行時点スナップショットを保存
7. 発行台帳を1枠減算
8. PDF生成ジョブ／保存対象を確定
9. 成功時だけコミット
```

- 途中失敗時は採番、発行レコード、台帳減算をすべてロールバックする。
- 同じ冪等性キーの再送で二重発行・二重減算しない。
- 残高が0未満になる更新をDB制約とロックで防止する。
- 発行成功後にPDF保存が失敗した場合の状態を明示し、同じ発行IDで安全に再生成できるようにする。

## 7. 連番、再発行、訂正、失効

### 7.1 連番

- 保証書・施工証明書は中央採番した一意な連番を持つ。
- PDF上部、フッター、QR照合データは同じ連番を表示する。
- 店舗側で任意の番号を入力・変更できない。
- 欠番が発生しても番号を再利用しない。

### 7.2 再発行

- 同一内容の再ダウンロード・再印刷は同じ連番を使う。
- 再印刷だけでは発行枠を追加消費しない。
- 再印刷回数、実行者、日時を監査ログへ残す。

### 7.3 訂正

- 発行済みデータを上書きしない。
- 旧版を失効または訂正前版として保持し、新しい版を関連付ける。
- 訂正理由、申請者、承認者、日時を記録する。
- 新規枠消費または枠返還の扱いはスーパーアドミン承認ルールに従う。

### 7.4 失効・枠返還

- 店舗の自己判断だけで発行枠を自動返還しない。
- 失効は履歴を残し、公開照合画面へ反映する。
- 枠返還はスーパーアドミンが理由を確認し、承認した場合だけ別台帳行で行う。
- 不正疑いによる失効は原則として枠を返還しない。

## 8. 発行時スナップショットとPDF保存

発行済み帳票は、後日の店舗設定・商品名・規約・ランク変更で表示内容が変わってはならない。

発行時に最低限、次を固定保存する。

- 顧客情報（必要最小限）
- 車両情報、車台番号またはマスク表示用情報
- 施工日、発行日
- 製品名、SKU、ベース／トップ区分
- 店舗名、住所、連絡先、インボイス番号
- 店舗ランクと割り当て済みランクロゴ
- 店舗ロゴ
- 保証規約バージョン、保証期間、適用条件
- 連番、発行者、発行元作業ID
- 発行可能枠を消費した商品と台帳ID

生成後のPDFはprivate Storageへ保存し、次を記録する。

- bucket / object path
- MIME type、byte size
- SHA-256
- 生成日時
- テンプレートバージョン
- 発行リビジョン

Storageオブジェクトの上書き保存は禁止する。訂正版は新しいパスへ保存する。

## 9. ロゴと店舗ランク

### 9.1 ランクロゴ

保証書には、スーパーアドミンが店舗へ割り当てた次のいずれかのランクロゴを使用する。

- GYEON Certified
- GYEON Detailer
- GYEON Shop

- 店舗ユーザーはランクロゴを選択・変更できない。
- ランクとロゴ資産はサーバー側の有効期間付き割り当てから解決する。
- 発行時点のランクとロゴをスナップショット化する。
- 発行後に店舗ランクが変わっても、過去PDFのロゴを差し替えない。

### 9.2 店舗ロゴ

- 店舗ロゴとGYEONランクロゴは別の資産として扱う。
- 特定店舗（OFFICE AZ等）のロゴや会社情報をテンプレートへ固定しない。
- 認証中の店舗設定から解決し、他店舗のロゴを表示できないようにする。
- ロゴは縦横比を保持し、切り抜き・引き伸ばしを行わない。

## 10. QRコードと公開照合

保証書・施工証明書には真正性確認用QRコードを付ける。

- QRコードは推測困難な公開照合トークンを含むHTTPS URLへ遷移する。
- DB主キー、dealer_id、顧客IDを直接URLへ含めない。
- 公開画面では個人情報を最小限またはマスクして表示する。

公開照合画面の表示項目:

- 帳票種別
- 連番
- 有効 / 訂正済み / 失効
- 発行店舗名と発行時ランク
- 施工製品
- 施工日
- 車両識別情報の一部（例: 車台番号末尾）
- 最新リビジョンの案内

公開画面から住所、電話番号、メールアドレス、完全な車台番号、内部IDを取得できないこと。

## 12. 不正検知

次の条件を監視し、スーパーアドミンへ警告できる構造にする。

- 短期間に集中した大量発行
- 購入付与直後の全枠消費
- 同一車両・同一施工への重複発行試行
- 失効・訂正・再印刷が多い店舗
- 購入履歴と発行実績の比率が通常範囲から大きく外れる店舗
- 発行停止中の商品・店舗からの試行
- 他店舗の顧客、車両、ロゴ、作業IDを使う試行
- 管理者による大きな手動調整

警告は自動失効の根拠にせず、管理者確認のための証拠として扱う。ただし明確な権限違反や残高不足は発行を拒否する。

## 14. セキュリティ要件

- 店舗データはdealer_idで完全分離し、RLSとサーバー認可を併用する。
- 発行・残高減算・採番はブラウザから直接DB更新させない。
- スーパーアドミン操作は通常店舗権限から分離する。
- service roleをクライアントへ公開しない。
- PDF Storageはprivateとし、短時間の署名URLまたは認可済みサーバーダウンロードを使う。
- 発行済みスナップショットと台帳を通常のUPDATE / DELETE対象にしない。
- 管理者操作も監査ログへ記録する。
- エラー時は残高、他店舗情報、内部ルールを過剰に返さない。
- 公開QR照合はレート制限とトークン失効に対応する。

## 15. PDFデザイン拘束条件

添付デザインは視覚的な基準として採用候補とするが、次を実装時に修正する。

1. OFFICE AZ等の会社情報・ロゴを固定せず、認証店舗の発行時スナップショットを使う。
2. GYEONランクロゴは管理者割り当てから解決する。
3. CanCoatは専用保証書として、承認済み保証文言を使う。
4. 上部とフッターの連番を完全一致させる。
5. 真正性確認QRコードを追加する。
6. A4縦で正しい改ページを行い、固定の`PAGE 01 / 01`を使用しない。
7. 公式フォント・公式ロゴ資産だけを使用する。
8. 規約文はGenspark生成文をそのまま法的確定文として採用しない。
9. PDFへ表示する製品は発行スナップショットから注入し、HTMLへ固定しない。
10. 発行済みPDFのバイト列を保存し、後日のテンプレート変更で再解釈しない。

## 16. 受入基準

実装完了には最低限、次の証明が必要である。

- 購入確定1回から商品ルールどおりの整数枠が1回だけ付与される。
- 同一購入の再処理で二重付与されない。
- 残高1で同時に2件発行しても成功は1件だけで、残高が負にならない。
- 発行成功時だけ一意な連番、発行レコード、台帳減算が同時確定する。
- 発行失敗時に枠が減らない。
- 再印刷で新しい連番と追加減算が発生しない。
- 訂正前PDFと訂正後PDFを両方追跡できる。
- 店舗Aが店舗Bの残高、作業、顧客、PDF、ロゴを参照・使用できない。
- レザー、ガラス、ホイール等からボディ保証書を発行できない。
- CanCoatは専用保証書へだけルーティングされる。
- 未許可ランクの店舗は対象保証書を発行できない。
- 失効した連番をQR照合すると失効状態が表示される。
- 発行済みPDFのSHA-256と保存バイトが一致する。
- ルール、店舗ランク、ロゴ、商品名を後で変更しても過去PDFが変わらない。
- スーパーアドミン調整は理由と操作者が必須である。
- 1件・複数製品の各帳票がA4として正しく出力される。
